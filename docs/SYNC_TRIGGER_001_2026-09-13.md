# SYNC-TRIGGER-001 — Foreground Realtime Wake-Up

**Status:** Completed

**Date:** 2026-09-13

**Model:** Sol

## Problem

`SYNC-LATENCY-FIX-001` reduced the time from a completed transaction pull to a visible UI update to a 69.5 ms median, but a foreground client still began work only on its five-second timer or the browser `online` event. Three physical traces measured 4.571–8.136 seconds from a cloud write to the receiving Android UI.

## Implementation

- `SyncProvider` subscribes to `public.synced_records` through Supabase Realtime after a user signs in. The subscription is filtered to that user's `user_id` and is replaced or removed when the authenticated user changes.
- A Realtime event wakes the existing serialized `sync()` path. Realtime does not apply data directly, so version validation, encryption, tombstones, cursor repair and store refresh behavior remain in `runFullSync()`.
- The five-second timer and `online` listener remain as recovery paths if the Realtime socket is unavailable.
- Realtime events received during an active pass are coalesced into one queued follow-up pass. The first physical implementation discarded those events; a live overlapping-write trace reproduced a 10.191-second fallback delay, which led to this correction before completion.
- Migration `20260913014500_enable_synced_records_realtime.sql` adds `public.synced_records` to the `supabase_realtime` publication idempotently. Existing row-level security continues to restrict records to `auth.uid() = user_id`.

## Physical Android Evidence

The final APK was installed in place on vivo V2348. A temporary encrypted transaction was created locally, its app-generated encrypted envelopes were used to simulate remote edits, and the receiving UI was observed from cloud publication through the transaction pull and store refresh.

| Trace | Cloud write start → UI | Cloud response → UI | Transaction pulls |
|---|---:|---:|---:|
| 1 | 1,038.4 ms | 751.6 ms | 1 |
| 2 | 1,209.5 ms | 1,043.9 ms | 1 |
| 3 | 2,693.3 ms | 2,504.9 ms | 1 |
| **Median** | **1,209.5 ms** | **1,043.9 ms** | **1** |

The cloud-write-to-UI median fell from 5,654 ms to 1,209.5 ms, a **78.6% reduction**. An explicit overlapping-write trace delivered the first update in 2,590.8 ms, queued the second event while that pass remained active, and delivered the final value after 6,681.9 ms with exactly two transaction pulls. This confirms the queued pass runs after serialization permits it instead of losing the event and waiting for a later polling interval.

The synthetic row was deleted after measurement. IndexedDB contained 32 transactions, the test identity was absent locally, and its cloud row was a terminal tombstone.

## Remaining Limit

Realtime shortens foreground wake-up time. Android may suspend the WebView and its socket while the app is backgrounded; the durable local-first data and polling/online recovery paths still reconcile when the app resumes. A remote change that arrives during a long serialized pass must wait for that pass to finish before the queued follow-up can safely begin.
