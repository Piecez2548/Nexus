| WORKOUT-003 | Workout Tracker | GPS Route Tracking | Medium | Completed | WORKOUT-001 |
| WORKOUT-004 | Workout Tracker | YouTube Demo Linking | Low | Completed | WORKOUT-001 |

> **WORKOUT-001..004, all delivered together (2026-08-17, `db65045`).** Planned via Plan Mode given the scope (four new subsystems: a two-table data model, an ephemeral timer state machine, GPS/map integration, and external-link handling) and reviewed with the user before implementation, mirroring the Vault entry above's approach for anything this size.
>
> **Data model — two tables, not one.** `WorkoutExercise` (catalog: name/category/icon/color/calorie rates/`youtubeUrl`/`gpsTracked`) + `WorkoutEntry` (log: `exerciseName` denormalized like `Transaction.category`, reps/rounds/durationMinutes/distanceMeters/route/caloriesBurned). Modeled after `Category`+`Transaction`, not `Habit`'s single-table shape, since a workout logs multiple entries per exercise per day (sets) rather than checking in once — see `db.ts` v20's own comment for the reasoning. `route: GeoPoint[]` lives inline on the row, same pattern as `Habit.completedDates`.
>
> **Timer and GPS tracker are both plain hooks, not Zustand stores or Dexie-backed** — `useIntervalTimer.ts`/`useGpsTracker.ts` hold ephemeral, single-consumer UI state (only their own drawer ever reads it), timestamp-based rather than per-tick-decrementing so neither drifts if a render is delayed. Both are explicitly foreground-only: no background service, no persistent notification, tracking/counting stops the moment the component unmounts — a deliberate scope cut stated in `docs/SECURITY.md`'s new Workout Tracker section, not an oversight.
>
> **YouTube linking, no API integration.** `buildYoutubeUrl()` uses an explicit per-exercise URL when set, else auto-builds a YouTube search from the exercise name — no API key/quota needed. Verified that plain `window.open()` doesn't work on this app's stock Capacitor Android setup (no `WebChromeClient.onCreateWindow` override) — added `@capacitor/browser` as a new dependency to open the link in the system browser correctly on native.
>
> **GPS tracking is genuinely new territory for this app** — first feature requesting device location. Added `@capacitor/geolocation` (foreground `watchPosition`, standard runtime permission — no special-access Settings flow like Notification Access) and `leaflet`+`react-leaflet` for the map (OpenStreetMap tiles, no API key/billing account, same reasoning as the YouTube fallback). `ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION` added to `AndroidManifest.xml`. Distance is a pure Haversine-formula summation over consecutive route points (`gps/distance.ts`), not a third-party geo library.
>
> **A real build-breaking mistake, caught only by actually assembling the APK, not by any earlier check**: the new `AndroidManifest.xml` permission comment used `--` inside an XML comment (invalid per the XML spec — the exact same bug class fixed once already this session, commit `081dfdc`), which passed `tsc`/`oxlint`/`vitest`/`npm run build` cleanly and only broke `:app:processDebugMainManifest` at Gradle assembly time. Fixed by rewording the comment; flagging the pattern explicitly here since it's now recurred twice — any future native-file XML comment in this project should avoid `--` on principle, not just fix it reactively again.
>

## Gallery Scanner — Post-Launch Stabilization (post-PLT-020)

Not new MASTER_TASK items — real on-device use of the shipped scanner (the open item PLT-020 flagged) surfaced bugs, which were fixed as they were found, followed by two code-review passes over the whole QR/OCR pipeline. Recorded here rather than as new GS/PLT ids since the epic itself is unchanged (still 50/50 + 20/20).

> **On-device bug-fix round** (`a71d6cb`, `343f162`, `9d95994`, `7b9013f`, `ee45134`, `1e59da6`, `dfcc096`) — the native picker (PLT-020's open item) was verified on-device and several real-slip failures were found and fixed: a QR-decode canvas-fallback bug that silently broke on-device decoding (some Android WebViews lack `OffscreenCanvas`, so `imageDataQrDecoder`/`qrRecovery` gained a DOM `<canvas>` fallback); an amount-extraction bug picking the wrong 2-decimal number off a slip ("20 → 520") fixed by anchoring to a currency marker or amount label; "Unknown bank" on real slips (Thai completed slips carry a *slip-verification* QR, not an EMVCo payment QR, so `identifyBankFromText` was added as an OCR-text fallback, earliest-keyword-wins so the payer's own bank beats a bank name embedded in a merchant string); imported-row quality (title/category/grammar, full-resolution + max-quality gallery image picking for OCR); and `slipParser.ts` merchant extraction extended from shop-keyword matching to positional extraction (name/bank/account → payee) so label-less e-wallet/person/top-up payees (e.g. a PromptPay/G-Wallet top-up) resolve to the payee's name instead of falling back to the bank name.
>
> **Code-review pass 1** (`dbe4ca2`) — a 10-agent parallel review of the whole QR/slip-scanning system, then fixed: `identifyBank()` could never match a real (non-PromptPay) bank from EMVCo (no `aidGuids`/`match` were ever populated for the real-bank registry entries) — now falls back to OCR-text identification when a clean EMVCo payload still leaves the bank unresolved; the category-learning store (GS-045/043) was fully disconnected from the import flow — wired (read side) into `candidateToTransaction`/`GalleryScanFlow`, and the guessed category is now validated against the user's live category list (falls back to "Others" rather than persisting a category that doesn't exist, e.g. the categoriser's "Healthcare"/"Bills" vs. the app's default-seeded "Health"/"Utilities"); a `??` vs `||` inconsistency silently broke category fallback on an empty merchant; OCR preprocessing (`ocrPreprocess.ts`) hard-binarised every image unconditionally, which could wipe an overexposed slip to blank — now runs the existing (previously unwired) `enhanceIfNeeded` adaptive brightness/contrast correction first; `qrRecovery.ts` (GS-026) and `ocrFallback.ts` (GS-012) were built and tested but never called from production — wired into `extractSlipCandidate`; a shared `engine/image/canvas.ts` was extracted (three independent copies of the OffscreenCanvas/DOM-canvas fallback and the luma formula had drifted); several `slipParser.ts` edge cases (unanchored date regex fabricating a year from digits inside an account/reference number, an overly strict account-line pattern, a payee's own bank-name line being captured as their name). 2038 tests.
>
> **Code-review pass 2** (`ec75eff`) — a second 5-agent review specifically of pass 1's diff, catching regressions pass 1 introduced: OCR-derived date/time were discarded when OCR ran only to resolve the bank (a CRC-valid EMVCo QR carries no date, so the transaction silently got today's date instead); the newly-wired QR recovery had no `try`/`catch`, so a canvas-transform failure could abort a whole gallery batch; `recoverQr` redundantly re-decoded the original bytes with the same decoder `detect()` had just tried (added a `skipOriginal` option); `imageEnhancer.ts` still hand-rolled `OffscreenCanvas` directly instead of the shared `canvas.ts` helper pass 1 added — so adaptive enhancement silently no-opped on exactly the WebViews that helper exists for; the broadened `ACCOUNT_LINE` label prefix could match an unrelated labelled digit line (e.g. a phone number) and mis-anchor the positional recipient scan — restricted to an account-label allowlist; `META_LINE`'s amount words (`ยอด`/`รวม`) could false-positive-skip a real name containing them — now require a trailing digit; the recipient label list was re-copied by hand instead of derived from the shared registry. 2039 tests.
>
> **Current status**: `tsc -b`, `oxlint`, the full test suite (2039 tests), and `npm run build` are all clean; the latest APK (post-`ec75eff`) is installed on-device. **Known remaining gap**: category learning is wired read-side only — nothing in the UI yet calls `categoryLearningStore.learn()` (no category field/picker exists in `ImportPreview`), so a user has no way to correct a guessed category and have it stick. ## Cloud Sync — Silent Push-Cursor Stall, Root-Caused and Fixed (2026-08-16, `1b6fd60`)

Not a GS/PLT id. A real two-device (desktop dev server + installed Android app, same account) divergence reported directly by the user: dashboard totals stopped matching between devices, with no error ever shown in Settings → Sync despite repeated manual "Sync Now" presses on both. Root-caused via live evidence (both devices' real `syncState` cursors read over CDP, plus a desktop backup export compared field-by-field) rather than guessed from code alone, per this file's established discipline.

> **Symptom, confirmed with real data before any code was read**: a `docs/DECISIONS.md`-documented cloud sync layer already exists (`src/features/sync/syncEngine.ts`, Supabase-backed, `SyncProvider.tsx` polling every 5s while signed in) — this was not a "build sync" request, it was "why isn't the existing sync converging." Ruled out, with evidence, before looking at the sync engine itself: encryption-at-rest mismatch (the desktop backup export contains zero `encryptedContent` fields — the feature was never enabled on either device), cross-device foreign-key drift (`Transaction.category`/`.account` are stored as plain name strings, not local Dexie auto-increment ids, so they're portable across devices by construction), and the new Payment Notification Capture feature bypassing the sync-safe write path (traced `defaultSmartImportDeps.createTransaction` → `transactionService.create` → `createCrudService`'s `repository.add` → `encryptedRepository`'s `add` → `withSyncMeta` — the exact same path every other transaction-creating call site uses; confirmed, not assumed). Direct evidence instead pointed at the sync engine itself: both devices' `syncState` table (read live over Chrome DevTools Protocol on the phone, and via a user-run console snippet on desktop) had `push:transactions` and `pull:transactions` cursors stuck at effectively the same timestamp (~13:36 UTC), hours before the investigation, despite real new transactions existing locally on the phone after that point.
>
> **Root cause, reproduced with a failing test before any fix was written**: `pullTable()`'s cursor-advance logic nudges this device's own `push:<table>` cursor forward whenever it pulls a row, specifically to avoid redundantly re-pushing a row it just received unmodified (an intentional, already-tested behavior — see the "does not re-push a row it only ever received via pull" test). But that cursor is a single scalar watermark per table, not a per-row marker: it cannot distinguish "this specific pulled row is now in sync" from "everything with an earlier `updatedAt` is already pushed." If this device also has its own local, not-yet-pushed row whose `updatedAt` happens to be *earlier* than the row just pulled — realistic whenever a background writer (here, Payment Notification Capture, which can create a transaction at any moment, including mid-sync-pass) races against another device's write reaching this device via pull — the nudge silently advances the push cursor past that unrelated pending row. Since the cursor only ever moves forward and `pushTable()`'s query is `updatedAt >= cursor`, that row is then permanently excluded from every future push, with no error anywhere: the upsert that never happens can't fail.
>
